# Runtime 容量与恢复基线

票 #32，批次 C。先定阈值、再测量，然后才决定要不要改锁范围。本页第一版只有阈值与测法，在任何一次测量之前提交；结果在后续提交里追加，阈值不随结果改动。

## 对象与口径

- **试点规模**：一家公司（一个 scope），约 20 名人员加少量 Agent 同时使用；另有一家公司共用同一个 API 进程与连接池，用来看跨公司影响。
- **环境**：本机隔离栈（`acceptance/runtime/infra.py up`），API 单进程；测试专用启动器 `acceptance/runtime/server.py` 可以在拿到 scope 栅栏之后挂起一个事务，用来模拟慢事务。
- **计时**：
  - 客户端从发出到收到响应；
  - 服务端按运行记录 `governed_transaction` 的取连接、等锁、持有时长。
- **不代表**：
  - 目标环境的绝对性能；
  - 多进程或多副本的行为；
  - 数据库、对象存储的故障切换。

## 阈值（测量前确定）

| # | 场景 | 通过条件 |
|-|-|-|
| T1 | 无争用的单个请求 | 读 p95 ≤ 150 ms；写（prepare 加 commit）p95 ≤ 400 ms |
| T2 | 同一家公司 8 个客户端并发读，各 25 次 | 全部成功，吞吐 ≥ 50 次/秒 |
| T3 | 公司 A 的栅栏被慢事务占住 10 秒，且另有 8 个请求排队 | 公司 B 的读零错误，p95 不超过 B 自身基线的 3 倍 |
| T4 | 等锁上限 | 没有请求等 scope 栅栏超过 `GOVERNED_LOCK_TIMEOUT_MS` + 1 秒；超时的请求返回 503 |
| T5 | 对象存储每个响应延迟 2 秒 | 证据上传成功；上传期间同一家公司的读 p95 ≤ 500 ms |
| T6 | 撤权与在途请求竞争 | 撤权提交后开始的事务一律按新权限判定，被撤者读取被拒；撤权提交前已拿到栅栏的事务按旧权限完成 |
| T7 | API 进程被强杀 | 10 秒内恢复健康；用同一幂等键重放写请求，返回原回执；对象数与回执数一致，没有半截写入 |

各场景分两种配置各跑一次：

- **V0**：关掉锁与语句超时（`GOVERNED_LOCK_TIMEOUT_MS=0`、`GOVERNED_STATEMENT_TIMEOUT_MS=0`），近似改动之前的行为；
- **V1**：当前默认值（5 秒、30 秒）。

锁范围若有改动，再加一种配置重跑，结果另列。
