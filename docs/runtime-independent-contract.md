# Governed Runtime independent acceptance contract v0.1

Implementation scope: one business domain commitment/feedback loop, independent of Clark. This is an implementation and acceptance contract, not a production release claim. Existing compatibility routes and existing Working Memory behavior are preserved. No new production dependencies are required.

## Authority and implementation boundaries

- New implementation belongs to `src/memory_service_runtime/governed/`, migration `0016_governed_runtime.sql`, and is included from `memory_service_app.main` as `/v1` native routes. Existing infrastructure queue remains reusable.
- PostgreSQL is authoritative. Real versioned S3/MinIO stores evidence bytes. All new state changes go through authenticated HTTP commands. No LLM or graph database is required for this gate.
- An opaque, randomly provisioned bearer credential resolves a database principal (human/agent), scope and current active assignments. Only credential digests are stored. Requests cannot choose actor, role, tenant or company. This is the pilot identity adapter; external SSO integration is separate.
- Company/domain membership can contain zero or multiple people. Each commitment specifies the precise two required assignment IDs, from different humans, with roles CEO/DOMAIN_DRI for BusinessCommitment and DOMAIN_DRI/MISSION_DRI for ExecutionCommitment. Role assignments include scope, domain, active flag and validity interval.
- Scope auth_epoch row is locked for every authorized transaction; writes and revocation serialize on this fence. Recheck current principal and assignments after acquiring it. Old receipts and snapshots must also reauthorize. Simple per-scope serialization is acceptable for this pilot and must be documented.
- Runtime DB user is not superuser, owner or BYPASSRLS. New business tables have ENABLE and FORCE ROW LEVEL SECURITY with scope setting established only after credential resolution; explicit scope/domain checks remain in application code. Immutable revisions/receipts/handshakes/acceptances/history cannot be overwritten through app grants or commands.
- Existing compatibility APIs remain outside the new write authority. New `gov_*` records do not silently migrate existing WM/Clark records.
- Pilot DecisionRight is an explicit, stored versioned role/action/domain allowlist, including a VERIFIER role; arbitrary same-domain humans are not verifiers or closers. A supplied activation policy must match the policy applicable to this scope/object/action, not merely exist.
- Bootstrap may establish an already-confirmed CompanyOutcome as a starting fact. Every tested commitment, feedback and adjustment transition is still generated through HTTP.

## API and shapes

The four core action envelopes and typed support actions are defined in [models.py](../src/memory_service_runtime/governed/models.py) and the exported [OpenAPI](../contracts/openapi.json). UUIDs are stable identities, body extras are forbidden, integers reject bool/coercion. Support action schemas are typed, not unrestricted state patching.

`POST /v1/actions` accepts:

```json
{"action_type":"accept_commitment","target":{"object_id":"uuid","expected_version":1,"revision_id":"uuid"},"expected_versions":[],"idempotency_key":"unique-key-at-least-16","reason":"reason at least 5 chars","params":{"party_assignment_id":"uuid","understanding":"understanding at least 10 chars","accepted_terms_hash":"64-hex"}}
```

Creation support actions have `target:null`; existing-object actions require exact current target version and a revision that belongs to that object. `expected_versions` supplies all additional mutable/read dependencies. Reject duplicate IDs and mismatched target duplicates. Runtime derives the required dependency set rather than trusting the client list; `/v1/actions/prepare` may return this set for a proposed command without mutating business state.

Success: `{receipt_id, action_type, actor_id, auth_epoch, status:"committed", result:{...}, object_versions:[{object_id,object_version}], effect_task_ids:[], recorded_at}`. Persist the immutable receipt in the same transaction as state, history and queue reservations. Replays return the same receipt after current read authorization; same principal/scope/key with a different payload or action returns 409 IDEMPOTENCY_CONFLICT. Do not include current mutable task status in the frozen receipt; expose it separately when reading receipt status.

Errors: `{error:{code,message}}`, with 401 UNAUTHENTICATED, 403 FORBIDDEN, 404 NOT_FOUND (also inaccessible cross-scope objects), 409 VERSION_CONFLICT/IDEMPOTENCY_CONFLICT/INVALID_STATE/DEPENDENCY_MISSING/STALE_DEPENDENCY, 422 INVALID_REQUEST, 503 EVIDENCE_UNAVAILABLE. No raw SQL, credentials or external responses in errors.

Read endpoints:

- `GET /v1/objects/{id}`: head with object_type, lifecycle_status, object_version, latest_revision_id, effective_revision_id and accessible payloads.
- `GET /v1/objects/{id}/revisions/{revision_id}`: immutable revision, payload_hash and server recorded_at.
- `GET /v1/action-receipts/{id}`: frozen receipt plus separate current effects list.
- `POST /v1/context-packs`: `{object_ids:[],valid_at:"ISO8601",known_at:"ISO8601"}`; return context_snapshot_id, exact selected revisions and source references. Historical content must be filtered using known_at, no latest-content substitution. Historical authorization always uses current rights. `GET /v1/context-packs/{id}` reauthorizes every referenced object/evidence. It may store snapshots instead of implementing a response cache initially; no cached content may bypass checks.
- `POST /v1/evidence-assets`: `{domain_id,title,content_base64,media_type}`; validate size/encoding and actually store bytes in versioned Object-Locked S3, record bucket/key/version_id/sha256/length. Result contains evidence object and revision IDs, no presigned URL. `GET /v1/evidence-assets/{object_id}/revisions/{revision_id}` downloads exact bytes after authorization and hash verification. A failed metadata transaction may leave an unreferenced S3 version; never invent a successful evidence record.

## Support commands and state rules

The implementation must publish exact Pydantic/OpenAPI schemas and a small fixture/client helper before acceptance tests are written. Minimal support actions:

1. `create_object`: params `{object_type,domain_id,payload,valid_from?}`. Allow only CompanyOutcome, BusinessCommitment, ExecutionCommitment, FeedbackThread, ManagementAdjustment, Decision, MetricObservation for this gate. CEO/DOMAIN_DRI prepare the business chain; agents can propose FeedbackThread/MetricObservation but cannot confirm decisions/commitments/closure. Commitments payload has `required_assignment_ids`, `upstream_refs:[{object_id,revision_id}]`, `title`, plus terms. ManagementAdjustment payload has `feedback_revision_id`, `changes:[{object_id,from_revision_id,to_revision_id}]`, `decision_revision_id`. Decision must have a human confirmation support action (`confirm_decision`) before being used. Unknown object types and forged state fields are rejected.
2. `propose_revision`: creates an immutable candidate for same object; payload references upstream exact revisions. Optional `bundle_id` binds a commitment candidate to a ManagementAdjustment; a bundle-bound revision cannot activate individually. Every content change increments object_version; old effective pointer remains.

   Bundle preparation order is explicit: create a ManagementAdjustment draft shell with an empty changes list; create BC/EC candidates bound to its stable ID; propose a complete ManagementAdjustment revision containing those candidates and the confirmed Decision. Only that complete revision may be confirmed. The shell itself is never an applied adjustment.
3. `accept_commitment`: exact original schema; assignment must belong to caller, be current, match required party and role/domain; accepted hash equals revision hash. Creates immutable handshake, increments version, never activates. Repeated new-key acceptance for same assignment/revision does not fabricate another vote.
4. `activate_commitment`: exact original schema; checks all required distinct-human handshakes for the same revision/hash, current assignments and stored activation policy revision. Checks upstream versions and effective references. Only authorized human CEO/DOMAIN_DRI can activate. Changes effective pointer, lifecycle active, adds effective event and an infrastructure queue outbox task in the same transaction.
5. `route_feedback`, `accept_feedback`, `investigate_feedback`: explicit transitions open -> routed -> accepted -> investigating. Route chooses a valid responsible assignment; only assigned human can accept/investigate. Existing revision remains immutable; lifecycle events are appended and object_version increments.
6. `confirm_adjustment`: exact original schema; target is ManagementAdjustment revision. Checks confirmed same-domain Decision, same current FeedbackThread revision, complete changes equal the immutable adjustment payload, all affected expected versions and reverse active dependents so omitting EC when its BC changes is rejected. Every candidate has required signatures. Validate internal dependencies against the proposed post-commit bundle, external dependencies against current effective revisions. Apply every changed pointer, adjustment applied and feedback awaiting_acceptance atomically, with receipt/history/outbox. At least one named checkpoint after first object update permits test-only rollback injection.
7. `record_acceptance`: params `{decision_revision_id,evidence_revision_ids,verification_result}` on FeedbackThread; requires independent authorized human verifier, not the feedback assignee, implementer or any proposer/author of the applied adjustment/affected candidate revisions. Match the resolution decision and evidence to feedback/adjustment processing scope; all relevant external effects must have succeeded. Result accepted/changes_requested. Record immutable acceptance including exact feedback/decision/evidence and processing scope. An accepted record is required for closure, changes_requested returns to investigation.
8. `confirm_closure`: exact original schema; validate authorized human closure right, current accepted record, same processing scope/decision/evidence, genuine accessible S3 bytes and completed effects. resolved/no_change -> closed, dismissed -> dismissed; close is not inferred from task delivery. no_change/dismissed require explicit confirmed resolution Decision, and a `request_feedback_acceptance` support command from investigating sets resolution scope without an adjustment. Keep dispositions separate. `reopen_feedback` is explicit authorized transition, preserves earlier closure/acceptance and invalidates their reuse through a processing-cycle identity.
9. `record_observation` or MetricObservation create/propose support: stores numeric value, metric identity, valid interval and server recorded_at; correction creates a new immutable revision. Context read at known_at before correction returns prior content, afterwards returns correction; future valid observations are excluded. Do not let callers choose recorded_at.
10. `revoke_assignment`: CEO-authorized command on a scope/assignment (dedicated typed params if target:null) marks it inactive and increments auth_epoch atomically. Self-revocation policy can reject rather than invent a new admin. Recheck all object, snapshot, evidence and receipt reads after revocation, plus writes and replay. Multi-domain grants must not leak another domain.

## Worker and failure injection

Reuse `runtime_tasks` as transactional outbox via enqueue_task on the caller transaction, and RuntimeWorker claim/retry/lease fencing. Register a `governance.dispatch` allowlisted handler. Its destination comes only from trusted server configuration `GOVERNED_EFFECT_URL`; payload cannot select a URL. Send a stable effect key to a test HTTP receiver with a durable SQLite/Postgres ledger; repeated deliveries return same result and create only one ledger row. This receiver represents the external system in the acceptance environment, not real business execution.

Before dispatch, resolve the receipt's actual principal and required assignments from the database and check current permission under the same auth fence. If revocation committed first, dispatch must not happen. For this single-domain pilot it is acceptable to hold the fence across a bounded HTTP request (short timeout), explicitly documenting the throughput tradeoff. Actor-supplied task payloads cannot grant execution rights. Worker retry after a previously permitted external success still uses the same effect key and reconciles through the durable receiver.

Production runtime can expose no-op `checkpoint(name, context)` callbacks for instrumentation, never user-selectable state bypasses. Acceptance wrappers may replace callbacks and pause/fail using local barrier files, require a test secret for any test-only request headers, and are not imported by the production main module. Named checkpoints: auth_fence_acquired, before_business_commit, after_first_bundle_update. Response-loss is tested at an HTTP proxy after server commit. Worker crash is injected after external receiver commits but before worker acknowledges task, then real process kill/restart and lease expiry prove replay.

## Required independent gate

Eight groups: separate two-party handshake/activation; complete atomic adjustment + rollback; concurrent CAS requests from independent HTTP clients; idempotency after dropped response; evidence-backed independent acceptance/closure including no_change/dismissed/reopen; revoke + old context/receipt/evidence + auth race; valid_at/known_at history + source revisions; actual worker crash/retry, stop/start persisted DB/object data. Also run original relevant/full tests, fresh migration replay, application-role RLS checks and a separate backup/restore rehearsal into a second disposable database/bucket or an explicitly reported limit.

Seed only identities, role/policy records and starting facts. Do not preseed successful handshakes/receipts/closed objects. Save sanitized HTTP transcripts, receipt IDs, independent SQL assertions, S3 hashes, receiver ledger, versions and fault times per test_run_id. A PASS must be derived from real assertions, not hardcoded final snapshots or the implementer's own report. Label local runtime acceptance separately from Clark integration, staging, production and external SSO.
