# 取上下文的留痕在 world 0.1 内只增不删，按量监控；归档与清理随下一个协议版本定

world 0.1 规定，每次取上下文（`POST /v1/world/objects/{id}/context`）都在 `gov_world_context_packs` 落一行：问题、上下文包、检索计划、六问覆盖与预算记录。Agent 的回答凭 `context_pack_id` 引用这一行，追溯「当时给 Agent 看了什么」。

- **每行的大小**：E&O 九月实验里约 5.6 万字符的 JSON。其中分层内容约 3.9 万，Markdown 约 7,600，检索计划约 5,700，覆盖约 3,000。
- **不可改**：表上有禁止 UPDATE/DELETE 的触发器。world 0.1 独立验收的「不可变历史」门槛也断言，连控制面也改不了。
- **评估的意见**：两份外部评估都指出，这张表没有保留期，也没有清理路径。

## Decision

- **world 0.1 内只增不删。** 这一行是审计记录，删掉就无法回答「那次回答依据的是什么」。给控制面开删除口，会推翻 0.1 验收的门槛，也会改变契约里「上下文包留存」的含义。
- **按量监控。** `tkos-governed-control status --scope-id …` 报出这家公司的上下文包行数、占用字节，以及最早、最晚时间。
  - 按实验的量估算：每次约 56 KB，每天 500 次约 28 MB，一年约 10 GB。这在试点规模下可以接受。
  - 每行的大小由服务端的预算约束：Markdown 12,000 字符、每个对象 10 条事件、近 30 天；请求本身不能把它撑大。
- **归档与清理随下一个 world 协议版本一起定。** 要先回答三个问题：
  - 为了追溯，哪些字段必须永久留在库里（包 id、引用、摘要）；
  - 整包导出到对象存储后，以什么留痕来允许清理；
  - 验收门槛如何随之改写。
- **重新评估的时机**：单家公司的上下文包超过 5 GB 或 100 万行，或 Agent 从试点转为日常使用。

## Considered Options

- **给控制面加按时间清理的命令**：被否。理由见上，它推翻 0.1 验收的门槛。
- **每行只存引用和 Markdown，不存分层内容**：属于 0.1 的投影形状变化，留给下一个版本。MCP 返回给模型的内容已按实验建议瘦身，但库里保存的仍是完整的包。

## Consequences

- 表会持续增长，运维要按 status 的数字盯住占用。
- 下一个 world 协议版本要带上归档与清理的设计，以及对应的验收改动。

## 补记（2026-09-25）：批次 D 加的字段

#32 批次 D 按第一轮实验的建议，给上下文包加了几项内容：

- 各层的 `hop`，即主干之外多取的一跳；
- 检索计划的 `hops`；
- 事件行的记录人与被指派者名字；
- Markdown 开头的六问指引。

这些都是加法：0.1 契约与验收依赖的字段一个没删、没改名，world 0.1 差异复验通过。上面说的「投影形状变化」指删减或重组字段（例如只存引用与 Markdown），仍留给下一个版本；只加字段不在此列。每行因此略大，第二轮实验报告拆解了 Markdown 增加的部分。
