# Runtime 容量与恢复基线

票 #32，批次 C。先定阈值、再测量，然后才决定要不要改锁范围。本页第一版只有阈值与测法，在任何一次测量之前提交；结果在后续提交里追加，阈值不随结果改动。

## 对象与口径

- **试点规模**：一家公司（一个 scope），约 20 名人员加少量 Agent 同时使用；另有一家公司共用同一个 API 进程与连接池，用来看跨公司影响。
- **环境**：本机隔离栈（`acceptance/runtime/infra.py up`），API 单进程；测试专用启动器 `acceptance/runtime/server.py` 可以在拿到 scope 栅栏之后挂起一个事务，用来模拟慢事务。
- **计时**：
  - 客户端从发出到收到响应；
  - 服务端按运行记录 `governed_transaction` 的取连接、等锁、持有时长。
- **不代表**：
  - 目标环境的绝对性能；
  - 多进程或多副本的行为；
  - 数据库、对象存储的故障切换。

## 阈值（测量前确定）

| # | 场景 | 通过条件 |
|-|-|-|
| T1 | 无争用的单个请求 | 读 p95 ≤ 150 ms；写（prepare 加 commit）p95 ≤ 400 ms |
| T2 | 同一家公司 8 个客户端并发读，各 25 次 | 全部成功，吞吐 ≥ 50 次/秒 |
| T3 | 公司 A 的栅栏被慢事务占住 10 秒，且另有 8 个请求排队 | 公司 B 的读零错误，p95 不超过 B 自身基线的 3 倍 |
| T4 | 等锁上限 | 没有请求等 scope 栅栏超过 `GOVERNED_LOCK_TIMEOUT_MS` + 1 秒；超时的请求返回 503 |
| T5 | 对象存储每个响应延迟 2 秒 | 证据上传成功；上传期间同一家公司的读 p95 ≤ 500 ms |
| T6 | 撤权与在途请求竞争 | 撤权提交后开始的事务一律按新权限判定，被撤者读取被拒；撤权提交前已拿到栅栏的事务按旧权限完成 |
| T7 | API 进程被强杀 | 10 秒内恢复健康；用同一幂等键重放写请求，返回原回执；对象数与回执数一致，没有半截写入 |
| T8 | 公司 A 排队的请求超过连接池上限（12 个，池 10） | 公司 B 的读全部在 `GOVERNED_LOCK_TIMEOUT_MS` + 1 秒内得到响应，零错误 |

T8 是在第一次测量之前补上的：批次 C 把池耗尽列为单独的场景，T3 的 8 个排队请求不会占满 10 个连接。

各场景分两种配置各跑一次：

- **V0**：关掉锁与语句超时（`GOVERNED_LOCK_TIMEOUT_MS=0`、`GOVERNED_STATEMENT_TIMEOUT_MS=0`），近似改动之前的行为；
- **V1**：当前默认值（5 秒、30 秒）。

锁范围若有改动，再加一种配置重跑，结果另列。

### 过程中的两处更正

- **T4 的判定口径。**
  - 改动前第一次运行按客户端总时长判 T4，把「等连接」也算进了「等栅栏」：V1 有一个请求先等连接约 5 秒，再等栅栏约 5 秒。
  - 在任何代码改动之前，跑器改为按服务端运行记录的等栅栏时长判定，再跑了一次（before-2），客户端总时长另列。
  - 阈值本身没有改动。
- **before-2 的 V1 仍然不过 T4。** 一个请求在没有等连接的情况下，等栅栏约 10 秒。
  - 原因：PostgreSQL 的 `lock_timeout` 按每次取锁计，排在别的等待者后面时要先等元组锁、再等持锁事务，最多等两倍。
  - 修正（90918ba）：取栅栏的整条语句另用 `statement_timeout` 限在同一上限内。

### 据此做的改动

改动与没有改动的部分都写在 [ADR-0006](adr/0006-scope-fence-scope-and-timeouts.md) 里：

- 等锁、语句都有上限，且取栅栏的整条语句受 `lock_timeout` 约束（T4、T8）；
- 证据字节移出栅栏（T5）；
- 读照旧取 `FOR UPDATE`（T2 在阈值内）；
- 外部效果派发暂留栅栏内。

旧 v0.2 的效果恢复（批次 C 的 R06）不在这条试点链上。按批次定义，这次不做，启用效果前另立 ADR。

### 没有覆盖的

- 目标环境的数据库、网络与存储；
- 多个 API 进程或副本；
- 数据库本身的重启与故障切换（T7 只强杀了 API 进程）；
- 长时间压测与内存增长。
