# tkos.world/0.1 静态截面实验报告：E&O 九月回放

> 2026-09-24 补记：按本报告的建议 1–4 与 6 调整后的第二轮三组对照，见 [world-v01-experiment-round2.md](world-v01-experiment-round2.md)。

票 #29。同一组六问、两种取法：

- **A 组**：Codex CLI 经 `tkos-world-mcp` 自行遍历，每问三次；
- **B 组**：服务端固定路径的取上下文，每问一次。

另量全量塞入的长度。本实验不作为 0.1 的验收门。数据摘要见 `docs/experiments/world-v01-static-cross-section.json`，跑器与指标的定义见 `experiments/world_v01/README.md`。

## 结论

五项通过标准里四项达标、一项不达标：

| 标准 | 要求 | 结果 | 达标 |
|-|-|-|-|
| 召回 | ≥ 0.9 | A 0.95（20/21）；B 0.95（20/21） | 是 |
| 可追溯 | 100% | A 100%（94/94 条断言） | 是 |
| 预算 | A 组长度 ≤ 全量塞入的一半，且不高于 B | A 平均每次 117,688 字符：全量塞入（86,029）的 1.37 倍，B 组 Markdown（7,390）的 15.9 倍 | **否**，六问全部超出 |
| 确定性 | ≥ 0.9 | A 1.00（三次取到的集合完全一致）；所引集合的一致率 0.74 | 是 |
| 八类反例 | 零出现 | A 0 次；两组都没取到任何诱饵 | 是 |

但这四项达标要打折看，原因有两条。

**第一，A 组实际上没有做「模型遍历」。**

- 18 次运行每次都调了取上下文，一共 35 次。
- 只有 1 次离开起点，读了所属 Task。其余都只对起点 Activity 调读工具，再把取上下文调第二遍。

所以，A 的召回、确定性与零反例，主要反映的是 B 的固定路径；八类诱饵基本没有经受检验。这是因为你让 A 组也能用取上下文，模型就几乎只用它。

**第二，取到了不等于用上了。** 另算了一项，它不在 `metrics.py` 里、不是通过标准，是写报告时另算的：标准答案应引用的项里，回答真正引用的只占 31/63（0.49）。

- Why 是 0/12：包里有 Mission、周期目标与 E&O 长期目标，回答却只拿 Task 的定义与 9/22、9/23 两场会解释「为什么」。
- Who 没有一次引 9/23 那场会，指派时间写成了播种时刻。这是 #28 定下的契约限制：指派的生效时间就是记录时刻。
- 现状、发生了什么，也各漏了 Mission 的状态、9/22 评审与 9/24 验收。

建议如下，按规格只调裁剪与标准句，不调对象结构：

1. **MCP 取上下文给模型的返回要瘦身**。这是超预算的主因。
   - 它现在返回约 5.6 万字符，按 JSON 转义后计：Markdown 只占约 7,600；结构化的层 39,061，其中钉定信息 5,451，比块正文 2,615 还多；检索计划 5,677；覆盖 3,001。
   - 给模型只返回 Markdown、包 id 与覆盖，按这次的调用方式估算，每次运行约 3 万字符；若不再重复调用，约 2 万。两者都低于全量塞入的一半（43,015）。
   - 注意：只要 A 用了 B 的包、又多读了任何东西，「A 不高于 B」就不可能成立。这一条只对纯模型遍历有意义。
2. **Why 的路径沿单元长期目标的 `goal_ref` 多取一跳**，带上公司级长期目标的定义类块。两组唯一漏掉的标准引用，就是公司级目标的「目标成果」块，每一次都漏。
3. **Markdown 里按问题组织**。比如开头就写出「为什么：Mission → 周期目标 → 长期目标」这条链。Why 0/12 说明，内容排在各层里，模型并不会自己拿来回答「为什么」。
4. **事件行写出记录人与被指派者的名字，不只给 principal_id**。Who 问里，模型为了把指派人的 id 对上名字，曾把取上下文的 `question` 当查询来用；那个参数只做记录，不影响包的内容。取上下文的工具说明也要写明这一点，并写明「同一问题取一次即可」。35 次取上下文里，13 次与同一运行之前的某次参数完全相同；另有 4 次只是改了预算或换了问题文字，返回的内容没有变多。
5. **标准句保持现状**。13 条 gap 断言都正确地引了空块或对象并说明「为空」，空块幻觉 0 次。
6. **下一轮加一组「A 不给取上下文」**，也就是原先的推荐方案。这样才能量出纯模型遍历，并真正考到诱饵。

## 实验设置

- **模型**：gpt-6-sol，推理档 medium；Codex CLI 0.155.0-alpha.16.4，于 2026-09-24 运行。
- **身份**：两组都以 E&O Agent 读，都只读。A 组的工具是取对象、取上下文、取事件、取状态，没有写工具。
- **A 组隔离**：
  - 每次都在空临时目录里运行，不读你的 Codex 配置，只读沙盒；
  - 关掉 shell、记忆、联网搜索、插件、apps、浏览器与子代理；
  - 凭证只经环境变量透传。

  事件流里出现 tkos_world 读工具以外的动作，就记为污染。
- **运行情况**：
  - 18 次全部有效：0 次污染，0 次失败，0 次重跑。
  - 每次耗时中位 31.6 秒，最长 360 秒，合计约 17 分钟。
  - 每次输入 token 中位 98,771。
- **基准**：
  - 播种内容哈希 `9ce66139…`，经 E&O DRI 批准（提交 `2d2dca7`），跑器核对了这次播种用的就是批准的内容。
  - 实验 scope 内有 25 个对象、48 条事件；按对象版本计，共有 41 个空块。
- **代码**：
  - 播种与批准是 `3fdbe83` 与 `2d2dca7`；跑器与指标是 `fdaeeab`，与运行时的工作区一致，已逐文件核对。
  - 这三个提交在标签 `world-v0.1-tickets` 上（PR #30 的分支头）；main 上是压缩合并的 `7e42004`。
  - API 进程用的是工作区源码，其中还有一处与 world 无关、尚未提交的叙述接口改动（`narrative.py`，默认关闭）。

## 逐问结果

长度单位是字符：

- A 组长度 = 一次运行里工具返回给模型的字符数，取三次的平均；
- B 组分两列：Markdown 是渲染后的上下文，也就是规格的预算口径；JSON 是经 MCP 返回的全部内容。

| 问 | A 召回 | A 可追溯 | A 确定性（取到/所引） | A 长度 | B 召回 | B Markdown | B JSON |
|-|-|-|-|-|-|-|-|
| Why | 9/12 | 14/14 | 1.00 / 0.78 | 120,580 | 3/4 | 7,396 | 55,851 |
| What | 9/9 | 20/20 | 1.00 / 0.79 | 120,580 | 3/3 | 7,396 | 55,851 |
| Who | 12/12 | 6/6 | 1.00 / 1.00 | 137,489 | 4/4 | 7,398 | 55,857 |
| 现状 | 9/9 | 14/14 | 1.00 / 0.58 | 101,883 | 3/3 | 7,380 | 55,803 |
| 发生了什么 | 12/12 | 16/16 | 1.00 / 0.60 | 105,071 | 4/4 | 7,380 | 55,803 |
| 凭什么 | 9/9 | 24/24 | 1.00 / 0.71 | 120,526 | 3/3 | 7,387 | 55,824 |

A 组每次运行的调用：

- 12 次：起点的取对象、取事件、取状态各一次，取上下文两次，两次参数完全相同。
- 3 次：调法同上，但第二次取上下文改了预算或换了问题文字。
- who-1：取上下文调了三次。
- now-2 与 happened-1：取上下文只调一次。happened-1 另外读了所属 Task 的事件与状态，是唯一离开起点的一次。

八类反例在 A 组的回答里都是 0 次，两组取到的诱饵也都是 0。

## 实测、推断与未验证

**实测**

- 上面所有数字，都由 `experiments/world_v01/metrics.py` 从 MCP 运行日志与结构化回答机械算出，没有模型打分，也没有人读回答。
- 「取到」只算带着内容回来的对象版本、块与事件，只以引用形式出现过的不算。取对象会顺带返回最新快照，快照也算取到。
- 两组唯一漏掉的标准引用是公司级长期目标的「目标成果」块。它只能经单元长期目标的 `goal_ref` 到达：取上下文的主干不取它，A 组也没往那边走。
- 取上下文经 MCP 返回的构成是上面第 1 条建议里列的数字，从一次运行的事件流里拆出来的。
- 94 条断言里 81 条 fact、13 条 gap。gap 断言都引了对应的空块或对象，没有 fact 断言引空块。
- 回答引用的覆盖（另算）是 31/63。期望引用若是整个对象，回答引了它的某个块也算。逐问：
  - Why 0/12；
  - What 9/9；
  - Who 6/12；
  - 现状 5/9；
  - 发生了什么 5/12；
  - 凭什么 6/9。

**推断**

- **A 重复调取上下文的原因**：事件流里没有模型的说明。改预算重调，像是以为第一次被裁了；原样重调的原因不明，未证实。
- **零反例不等于抗干扰**：诱饵大多在主干之外，比如别的单元的约束、无关 Mission 的状态、scope 外的对象。A 没离开主干，就碰不到它们，所以零次主要说明「没去」，不说明「去了也不会用」。
- **所引集合的一致率只有 0.74**：取到的内容三次完全相同，但每次挑来作证的引用不同。这是作答的措辞与取舍在变，不是取法在变。按报告采用的口径（运行日志里取到的集合），它不影响确定性结论。
- **长度的单位不一样**：A 与全量塞入按 JSON 计，B 的预算口径按 Markdown 计。即便 A 与 B 都按 JSON 比，A 也是 B 的 2.1 倍，结论不变。

**未验证**

- 只跑了一个模型与推理档；其他模型会不会同样只依赖取上下文，没有测。
- 回答内容对不对，没有逐句对照标准答案的文字。五项指标只看引用；指派时间写成播种时刻这类问题，是人工翻看 Who 的回答才看到的。
- 八类诱饵在「A 不给取上下文」时是否会被引用，没有测。这正是建议 5。
- 预算默认值（12,000 字符、每对象 10 条事件、近期 30 天）是否合适：这次 B 的 Markdown 远低于上限，没有触发裁剪。
- 没有部署到任何非本地环境，全部运行在本地隔离验收栈上的实验库里。实验库已在报告完成后删除。

## 复现

按 `experiments/world_v01/README.md`：

1. 用 `seed create` 建库，用 `seed run` 播种；
2. 用 `experiment run` 跑两组（`--model gpt-6-sol --effort medium`）；
3. 用 `experiment summarize` 重算指标；
4. 用 `seed clean` 删库。

标准答案须保持批准状态。输出目录是本地产物，不入库。
