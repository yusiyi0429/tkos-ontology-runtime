# 企业身份接入与正式 profile 的批准路径（待组织裁决）

这份 ADR 只提出方案，等组织裁决；在此之前不实现 SSO，也不放开正式 profile。

## 现状

**身份**：

- 每个主体（人或 Agent）在 scope 内有 Bearer 凭证，库里只存摘要。
- #32 起，凭证可设有效期，可由控制面签发、轮换、吊销（迁移 0038）。
- 人经本机治理工作台登录：账号文件把「用户名 + 随机登录码」映射到服务器上保管的个人凭证，会话在进程内存里，8 小时上限、闲置 30 分钟失效。
- Clark 适配层是一个静态 Basic 口令加一个统一的查看身份。

**正式数据**：

- 所有 profile 在 schema 里锁死 `record_origin = synthetic`、`corporate_approved = false`，迁移 0018 的 CHECK 只允许 `synthetic` 与 `legacy`。
- 系统在构造上只能承载合成的试点数据；要转正式，必须改 schema 并发版，不是改一个布尔值。

## 提议

### 1. 企业主体映射

- **做法**：在工作台一层接 OIDC；API 层保持 Bearer。
  - 新增映射表，记录「签发方 + subject → scope 内 principal」。
  - 登录后由服务端代用这个 principal 的短期凭证。凭证用 0038 的有效期，按会话签发，会话结束就吊销。
  - Agent 继续用长期凭证，按 0038 的轮换流程管理。
- **不采纳**：在 API 层直接验 JWT。改动面大，要重写 `authenticate` 与全部验收；目前只有工作台面对人。
- **待裁决**：
  - 用哪个身份提供方（飞书 / Lark、Google Workspace，或其他）；
  - 映射表由谁维护；
  - 离职或转岗后多久内必须吊销；
  - 工作台是否要支持多进程（那样会话就不能只放在进程内存里）。

### 2. 正式 profile 的批准

- **做法**：
  - 新的 profile schema 版本允许 `record_origin = corporate`、`corporate_approved = true`，但必须附一份批准记录：批准人、时间、批准的契约字节摘要、批准文书的引用。
  - 控制面的 `install-profile` 对这类 profile 要求这份记录，并记控制事件。
  - 迁移放宽 CHECK，但只对带批准记录的新 schema 版本放宽。
  - 已有的合成 profile 不变，也不能「升级」成正式的，只能另装一份。
- **待裁决**：
  - 谁有权批准（CEO、E&O DRI 或指定的委员会）；
  - 批准文书以什么形式存档；
  - 哪个协议先转正（建议从试点链 Method 0.5 开始）。

### 3. 正式数据路径

- 真实数据迁入沿用 `deploy/convergence/` 的只读盘点、演练与计划工具，先在演练库复跑，再按计划切换。
- **待裁决**：迁入范围、切换窗口、回退条件，以及由谁签字放行。

## Consequences

- 在裁决之前，本仓库的所有验收都只证明合成试点数据下的行为。
- 方案一旦裁决，需要一个新的协议或 profile 版本、一次迁移和对应的验收，按票推进。
