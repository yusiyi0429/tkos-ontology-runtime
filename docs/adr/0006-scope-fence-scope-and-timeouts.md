# 每家公司一把授权栅栏照旧；等锁有上限；证据字节移出栅栏；效果派发暂留栅栏内

每个治理事务在认证时对 `gov_scopes` 这家公司的那一行加 `FOR UPDATE`，读也一样。这把栅栏保证：

- 撤权提交之后开始的事务，一律按新权限判定；
- 事务在自己的持有期内看到一致的授权与对象状态。

两份外部评估都指出：这把栅栏加上栅栏内的对象存储与外部 HTTP 调用，会让一家公司近乎串行，一个慢事务还可能经连接池拖累别家公司。我们先按 [容量与恢复基线](../runtime-capacity-baseline.md) 定了 T1–T8 的阈值，再测量，然后做出下面的决定。

## Decision

1. **读照旧取 `FOR UPDATE`。**
   - 8 个客户端并发读同一家公司（T2），吞吐约 130 次/秒，p95 约 75 ms，已满足试点阈值。
   - 改成读取 `FOR SHARE` 能让同一家公司的读并发，但要先逐一核对每条 GET 路径都不写。试点规模下不值得这个风险。
   - 满足下列任一条件时重新评估：同一家公司的读 p95 超过 150 ms，或同时读取的用户超过 20 个。
2. **等锁和单条语句都有上限。**
   - `GOVERNED_LOCK_TIMEOUT_MS` 默认 5000，`GOVERNED_STATEMENT_TIMEOUT_MS` 默认 30000，都是事务内生效。
   - PostgreSQL 的 `lock_timeout` 按每次取锁计。排在别的等待者后面时，要先等元组锁、再等持锁事务，实测最多等两倍，所以取栅栏的整条语句另用 `statement_timeout` 限在同一上限内。
   - 超时返回可重试的 503，沿用 `EVIDENCE_UNAVAILABLE`。连接池耗尽早已用它表示「数据库暂不可用」，Clark 与工作台都按 503 重试。换一个新码，会让按错误码分支的调用方失配。
   - 请求体超限的 413 `REQUEST_TOO_LARGE` 是新增的状态，没有旧调用方依赖它，所以可以另起新码。
3. **证据字节移出栅栏。**
   - 上传分两段：第一段认证、判权、查登记；字节写对象存储；第二段重新认证、判权后落库，授权以第二段提交为准，与原先「写存储后再判一次权」一致。
   - 下载在栅栏内判权，提交后再取字节。
   - 对象键按内容寻址，上传可带幂等键。第二段被拒时对象存储里留下的版本不被任何记录引用，由 `tkos-governed-control evidence-orphans` 列出；保留期内只列不删。
4. **动作执行中校验证据完整性的读取（A3 交付与结果、Method、workspace 来源）仍在栅栏内。** 它们是动作判定的一部分，移出要先把校验与提交拆开；它们受对象存储客户端超时约束，别的等待者也受上面的锁上限约束。
5. **外部效果派发仍在栅栏内调用接收端。**
   - 效果要按当前权限派发。挪到栅栏外，要先定清认领、撤权竞争与重复投递的约束。
   - 试点链路不派发效果；派发连接已设同样的锁与语句上限，超限按可重试失败处理。
   - 在生产启用效果之前，另立 ADR。
6. **连接池每进程默认 10。**
   - 一家公司卡住时，靠等锁上限释放连接，别家公司不再等到取连接超时（T8）。
   - 部署时 API 与 Worker 的连接数之和要低于数据库的 `max_connections`。

## Considered Options

- **读取改 `FOR SHARE`**：能提高同一家公司的读并发。现在不做，理由见决定 1。
- **拿掉读取的栅栏、只在提交时复核权限**：撤权与在途读取的先后就不再确定，不采纳。
- **把外部效果调用移到提交之后**：需要可靠的认领与撤权复核设计，留到启用效果之前。

## Consequences

- 同一家公司的读仍然串行。管理后台轮询与 Agent 读上下文增多时，吞吐上限大约是每秒一百多次。
- 慢存储不再挡住同一家公司的其他请求。对象存储里可能留有未被引用的证据版本，要按对账结果处理。
- 超时的请求得到 503，调用方要按可重试错误处理。
